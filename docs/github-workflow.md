# GitHub 개발 관리

이슈 → 작업 브랜치 → 구현 및 검증 → PR → 자동 검사 → develop 병합 순서로 관리합니다.

| 항목 | 기준 |
| --- | --- |
| develop | 검증한 변경을 모으는 통합 브랜치. PR로 반영 |
| codex/issue-번호-설명 | 기능 또는 오류 수정 작업 브랜치 |
| main | 첫 발표·배포 때 생성하는 안정 버전 브랜치 |
| 이슈 | 원하는 동작과 완료 기준. 기존 관련 이슈가 있으면 재사용 |
| 커밋 | 의미 있는 변경 단위 |
| PR | 한 목적의 변경, 검증 결과, 제한, 연결 이슈 |
| 병합 | 자동 검사 통과 및 변경 검토 후 squash |
| 종료 | 이슈 종료와 병합된 원격 작업 브랜치 삭제 확인 |

main은 공개 데모 배포용 브랜치입니다. 첫 배포 준비 PR이 통과하면 검증된 develop으로 최초 생성하고, 이후 버전은 develop → main PR로 반영합니다.

Codex는 개발 중 이슈·브랜치·커밋·PR·검사 확인·일반 변경의 병합과 정리를 수행합니다.
제품 판단이 필요한 미해결 내용이나 검사 실패가 있으면 해결 전 병합하지 않습니다.
main 반영과 릴리스·배포는 사용자가 해당 작업을 요청할 때 진행합니다.

GitHub Actions가 PR과 develop/main 푸시마다 프론트엔드 빌드·린트 및 백엔드 테스트를 실행합니다.
자동 검사는 오류 탐지 수단이며 기능 화면의 검토를 대신하지 않습니다.
이 운영은 현재 개발 작업 중 수행하며 상시 백그라운드 감시를 의미하지 않습니다.

DB와 DB 백업, .env, 토큰, 개인 매장 사진 원본은 Git에 넣지 않습니다.
이미 끝난 작업은 기존 커밋 기록으로 보존하고 과거 PR을 소급 생성하지 않습니다.

## PR에 남길 자료

PR 템플릿의 요약·변경 내용·검증 결과·화면 및 검증 자료·제한·연결 이슈 형식을 사용합니다.
화면이 바뀌면 변경 후 스크린샷을 남기고, 전후 차이가 핵심이면 비교 화면을 첨부합니다.
데이터·백엔드·문서 변경은 관련 파일·응답·검사 링크로 설명할 수 있으며, 스크린샷이 없으면 이유를 적습니다.
제품 코드가 바뀌지 않은 PR에 새 제품 화면을 촬영한 것처럼 표시하지 않습니다.
스크린샷을 저장소에 넣은 경우 PR에는 GitHub에서 접근 가능한 파일 URL을 사용합니다.
채팅에만 표시한 로컬 경로는 GitHub 사용자가 볼 수 없으므로 증거 링크로 사용하지 않습니다.
