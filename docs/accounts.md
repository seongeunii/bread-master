# 계정 기능: 첫 구현

## 확정한 서비스 방향

- 이메일 + 비밀번호 로그인.
- 초기 권한은 관리자/근무자 두 가지. 점주·매니저·실장은 같은 관리자 역할.
- 한 사람당 한 매장, 초대 코드 입력 후 관리자 승인.
- 관리자는 소속 근무자의 풀이 수·정답률·최근 학습일을 확인.

회원가입·로그인·로그아웃·내 계정과 매장 생성·참여 신청·승인을 구현했습니다. 계정당 한 매장 또는 한 건의 대기 신청만 가능합니다. 매장을 만든 계정은 그 매장의 관리자가 되며, 해당 매장 신청만 승인·거절할 수 있습니다. 신청자는 승인 전에 취소할 수 있습니다. 관리자는 내 계정에서 매장 관리로 이동해 POS 배치와 근무자 현황을 확인합니다. 매장 메뉴 변경은 해당 매장의 도감과 연습에 적용됩니다. 가입 요청에 role이나 store_id를 넣어도 거부합니다.

## 사용 흐름

1. 로컬 API와 프론트엔드를 실행하고 상단의 '로그인 · 회원가입'을 선택합니다.
2. 회원가입에서 이름(공백 제거 후 1~30자), 이메일, 비밀번호(10~128자), 비밀번호 확인을 입력합니다.
3. 가입 성공 시 자동 로그인하고 내 계정을 표시합니다.
4. 새로고침 후 서버에 저장한 세션으로 계정을 확인합니다. 쿠키 유효기간은 고정 24시간입니다.
5. 로그아웃 시 현재 세션을 DB에서 폐기합니다. 폐기한 쿠키를 다시 보내도 로그인할 수 없습니다.

이메일은 앞뒤 공백을 제거하고 대소문자를 구분하지 않는 계정 식별자로 사용합니다. 이메일 소유 인증·비밀번호 재설정·계정 삭제는 아직 없으므로 실제 사용자 운영 전 별도 구현·정책 결정이 필요합니다. 비밀번호를 잊었을 때 운영자가 DB의 비밀번호 원문을 조회하는 기능은 없습니다.

## 코드 역할

| 위치 | 역할 |
| --- | --- |
| backend/app/auth.py | 입력 검증·비밀번호 해시·세션·인증 API·운영 설정 검사 |
| backend/app/db.py | 기존 DB를 보존하면서 users/auth_sessions/auth_attempts 테이블 추가 |
| frontend/src/features/account/AccountPanel.tsx | 가입·로그인 입력과 내 계정 화면 |
| frontend/src/features/account/useAccount.ts | 서버 로그인 상태 조회와 화면 상태 |
| frontend/src/lib/api.ts | 동일 출처 쿠키 전송, JSON 요청 헤더, 204 응답 처리 |
| backend/tests/test_auth.py | 실제 HTTP·쿠키·DB로 인증 경계와 재시작을 검증 |

Vite 개발 프록시는 `changeOrigin: false`로 브라우저의 Host를 보존합니다. 포트 5173 화면에서 포트 8000 API로 전달할 때 동일 출처 검사가 개발 환경에서도 일치하도록 하기 위한 설정입니다. 운영은 같은 HTTPS 주소에서 화면과 API를 제공합니다.

## API

| 메서드·경로 | 동작 |
| --- | --- |
| GET /api/v1/auth/session | 계정 기능 사용 가능 여부와 현재 계정. 비로그인은 user=null |
| POST /api/v1/auth/register | email/password/display_name으로 가입하고 새 세션 발급 |
| POST /api/v1/auth/login | 이메일·비밀번호 확인 후 세션 교체 |
| GET /api/v1/auth/me | 현재 세션의 계정만 반환. 비로그인은 401 |
| POST /api/v1/auth/logout | 현재 세션 폐기, 204. 이미 비로그인이어도 성공 |

가입·로그인·로그아웃 요청에는 `X-Bread-Client: web` 헤더가 필요합니다. 기존 api() 함수가 자동으로 보냅니다. 인증 API는 캐시하지 않습니다. 사용자 응답에는 ID·이메일·표시 이름·가입 시각만 포함하고 비밀번호·해시·세션 토큰을 반환하지 않습니다.

## 인증 방식

- FastAPI 공식 보안 문서에서 안내하는 pwdlib의 권장 Argon2 해시 사용: https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/
- JWT를 브라우저 저장소에 보관하는 대신 서버 세션을 사용합니다. 이 프로젝트의 단일 API에서는 로그아웃과 세션 폐기를 이해하기 쉬운 구조입니다.
- 브라우저는 HttpOnly·SameSite=Strict 쿠키의 무작위 토큰만 보관합니다. DB에는 토큰의 SHA-256 해시만 저장합니다.
- HTTPS 또는 BREAD_AUTH_COOKIE_SECURE=1에서는 Secure 쿠키를 사용합니다. 개발용 HTTP 로컬 서버에서만 비 Secure 쿠키를 허용합니다.
- 타 출처 Origin·cross-site 요청을 거부합니다. 커스텀 헤더와 CORS 사전 요청 차단도 사용하므로 인증 API에 임의 출처 CORS를 허용하면 안 됩니다.
- 로그인은 IP당 15분 30회·이메일당 15분 10회, 가입은 IP당 15분 10회로 제한합니다. 제한은 DB에 저장합니다. 같은 프록시를 공유하는 환경은 실제 신뢰할 프록시 설정과 제한 정책을 운영 전에 검토합니다.
- 로그인 실패는 계정 존재 여부와 관계없이 같은 메시지입니다. 가입 중복은 409로 안내하므로 가입 API의 이메일 존재 노출은 남아 있습니다. 실제 공개 운영 전 이메일 인증 흐름과 함께 검토합니다.
- 입력 오류 응답에는 Pydantic의 원본 input을 노출하지 않아 비밀번호가 오류 응답에 실리지 않도록 했습니다.

## 데이터 보존과 배포

로컬에서는 기존 backend/bread.db 또는 명시한 BREAD_DB_PATH를 사용합니다. 초기화는 테이블을 추가하며 기존 상품·문제·답안을 삭제하지 않습니다. 동일 파일을 유지한 재시작에서 계정·세션을 확인합니다.

**현재 Render 무료 체험 배포는 BREAD_DEMO=1을 유지**합니다. 이 모드에서는 회원가입·로그인·내 계정 API를 503으로 차단하고 화면에서도 로그인 메뉴를 제공하지 않습니다. 상품 조회·연습은 계속 사용할 수 있습니다.

Render 공식 문서에 따르면 무료 웹 서비스의 SQLite 파일은 재시작·재배포·절전 시 사라지고, 영속 디스크는 유료 서비스에서만 지원합니다. 무료 Render Postgres 역시 생성 후 30일 만료 제한이 있어 장기 보존 대안으로 확정하지 않았습니다.

- 근거: https://render.com/docs/free
- 단순한 초기 대안: 유료 단일 웹 서비스의 영속 디스크에 SQLite 저장. 디스크 비용뿐 아니라 웹 서비스 비용도 발생하며 백업·복구를 별도로 운영해야 합니다.
- 확장 대안: 관리형 PostgreSQL. 현재 SQLite SQL과 연결 코드를 이전하는 작업과 공급자·비용 검토가 필요합니다.
- 이번 작업에서 유료 리소스를 만들거나 실제 배포의 플랜·환경변수를 바꾸지 않습니다. 저장소 선택과 비용 승인을 받은 뒤 별도 배포 작업으로 연결합니다.

### 계정 운영 시작 조건

운영 환경(RENDER=true 또는 BREAD_ENV=production)에서 BREAD_DEMO=0인 경우 아래 설정을 모두 검사합니다.

| 환경변수 | 의미 |
| --- | --- |
| BREAD_PUBLIC_ORIGIN | 실제 HTTPS 웹 주소. 경로·쿼리·계정 정보 제외 |
| BREAD_AUTH_COOKIE_SECURE | 1 |
| BREAD_DB_PATH | /tmp가 아닌 실제 영속 저장소의 DB 경로 |
| BREAD_DATA_PERSISTENT | 영속 저장·백업 조건을 운영자가 확인한 뒤 1 |

BREAD_DATA_PERSISTENT=1 자체가 디스크를 생성하거나 영속성을 증명하지 않습니다. 실제 마운트·파일 권한·백업·복구 검증이 필요합니다. Docker의 실행 사용자 UID 10001에 해당 경로 쓰기 권한을 주고, 계정 운영 전에 재배포 후 복구까지 확인해야 합니다. 단일 작업자 운영을 전제로 하며, 여러 인스턴스로 확장할 때는 DB와 요청 제한을 재설계해야 합니다.

## 매장 학습 집계

승인된 계정으로 시작한 퀴즈 문항과 배달·POS 주문은 채점 시 한 번 집계합니다. 재고는 모든 상품 카테고리의 저장을 마쳤을 때 한 번 집계하며 정답률에는 포함하지 않습니다. 최근 학습일은 마지막 완료 시점입니다. 레벨은 누적 정답 0~9회에 1, 10~29회에 2, 30회 이상에 3을 표시합니다.

## 카테고리와 사진 등록

POS 메뉴 관리에서 카테고리 추가·이름 수정·순서 변경 및 빈 카테고리 삭제를 지원합니다. 상품이 남은 카테고리는 먼저 다른 분류로 옮겨야 합니다. 매장별 변경은 다른 매장에 영향을 주지 않습니다.

사진은 JPG·PNG·WebP 파일 5MB 이하를 업로드할 수 있습니다. 서버는 실제 이미지 형식을 검증하고 최대 1200px JPEG로 변환하며 원본 메타데이터를 제거합니다. 변환된 이미지는 매장당 32MB 한도로 DB에 저장됩니다. 업로드 후 메뉴 저장으로 연결합니다. 매장 소속이 승인된 사용자에게만 해당 매장의 사진을 제공합니다.

엑셀·CSV 일괄 등록을 추가했습니다. POS 사진 인식과 파리바게뜨 공식 상품 상세 링크 가져오기를 확인 화면에 연결했습니다.


## 파일 일괄 등록

POS 메뉴 관리의 엑셀·CSV 일괄 등록에서 CSV 양식을 내려받을 수 있습니다. 첫 행은 상품명,가격,카테고리,칸번호,사진주소이며 UTF-8 CSV 또는 XLSX 첫 시트의 최대 100행·2MB를 지원합니다. 칸번호는 1부터 시작합니다. 기존 카테고리와 이름이 일치하지 않으면 미리보기에서 선택합니다.

미리보기에서 행별 내용을 수정하고 확인한 메뉴 등록을 누르면 새 메뉴가 추가됩니다. 기존 상품과 칸이 겹치거나 행이 유효하지 않으면 전체 등록을 취소합니다. 같은 등록 요청을 재전송해도 메뉴를 중복 생성하지 않습니다.

## POS 사진 인식과 상품 링크

메뉴 관리의 파일·POS 사진·상품 링크에서 등록을 열고 가져오기 방법을 선택합니다.

POS 사진은 브라우저에서 한국어·영어 OCR로 처리합니다. JPG·PNG·WebP 5MB 이하, 1600만 화소 이하를 지원합니다. 원본에서 상품 칸 영역을 백분율로 지정하고 가로·세로 칸 수(각 1~5), 저장할 카테고리, 시작 칸을 정합니다. 칸별 이름·가격 후보와 신뢰도를 확인하고 오인식된 내용은 수정하거나 제외한 후 등록합니다. POS 분류는 직접 선택하며 개별 빵 사진의 자동 분리는 후속 범위입니다. 인식 모델과 WASM 코어는 첫 실행에 CDN에서 내려받습니다.

링크는 파리바게뜨 공식 상세 URL인 https://www.paris.co.kr/product/… 를 지원합니다. 서버가 이름·사진을 읽어 확인 화면에 표시합니다. 가격·카테고리·칸은 사용자가 입력하며 출처 URL을 함께 보존합니다. 임의 호스트·포트·이동 응답을 거절하고 읽기 시간과 응답 크기를 제한합니다.

실제 한국어 OCR 엔진은 합성 소보루·1,900원 이미지로 확인했습니다. 파일 선택 대화상자를 포함한 전체 브라우저 OCR 조작은 도구 제약으로 검증하지 못했습니다. 실제 POS 사진의 촬영 각도·글자 크기·조명에 따라 인식 결과가 달라집니다.
